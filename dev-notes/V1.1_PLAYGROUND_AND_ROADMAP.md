## Part 1 — Playground UI: Spec + Design Plan

### Why

A new user lands on the loopy-agent PyPI page, sees a `1.0.1`
badge, and has to make 10 decisions before they get a runnable
"hello world": choose a model, set an API key, write a `DAG`,
mount an `AgentLoop`, install the test model, configure the
gateway, set up a journal, decide which observability backend
to wire in, and so on. That's a 3-4 hour journey for the
"fast start" use case.

The Playground UI gives them a sandbox where every one of
those decisions is a one-click toggle. They can try the
features, see the resulting code, and then click "export to
GitHub gist" or "copy to clipboard" — at which point they
have a runnable starting point.

**Core insight**: a Playground is not a tutorial. It's a
**friction-free try-before-you-buy surface** that builds user
trust before they ever `pip install` anything. A Playground
that requires a server is a Playground that breaks; a
Playground that runs entirely in the browser is a Playground
that always works.

### Constraints (non-negotiable)

- **No Python in the browser** — the Playground is a static
  site (Next.js + TypeScript + shadcn). The Python runtime
  stays on the user's machine via `pip install loopy-agent`.
- **Zero server-side state** — no DB, no user accounts, no
  analytics. The only network call is fetching the loopy-agent
  wheel metadata from PyPI's JSON API (read-only).
- **Pyodide-driven runtime** — for the "try a feature" tabs,
  we run a JS-transpiled version of the loopy-agent Python code
  via Pyodide. Pure client-side; same code that ships in the
  wheel (compiled to JS via `py2wasm` or shipped as a
  pre-compiled wasm bundle).
- **Deterministic defaults** — the playground pre-fills
  `TestModel` everywhere. No API key, no network, no surprise
  cost.
- **Reproducible** — every playground run produces a
  copy-pasteable code snippet that works locally with
  `pip install loopy-agent`.

```
├──────────────────────┬─────────────────────────────────────┤

│  (Monaco / CodeMirror)│  (stdout, JSON, span tree)         │

│  ░░░░░░░░░░░░░░░░░░░  │  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░     │

└──────────────────────┴─────────────────────────────────────┘
```

#### Tab 1 — "Agentic Loop"

**The core demo.** User sees a 3-step Plan→Act→Reflect loop
running with `TestModel`. Presets:

- `hello world` — minimal AgentLoop
- `retry on failure` — demonstrates the Reflector + Tenacity
  integration
- `branching` — shows how policy_engine.gate() blocks a
  step in real-time
- `streaming` — generator + StreamChunk output
- `interrupt + resume` — AgentLoop with HITL pause

**Export**: a `main.py` they can `python main.py` locally.

#### Tab 2 — "Verified Agent"

**The T3.2 demo.** User sees a property-based verifier drive
the agent on 50 inputs and report pass/fail per case. Presets:

- `output_must_contain` — basic invariant
- `length bound` — `output_len <= 10 * input_len` over 50 cases
- `Hypothesis fuzz` — random bytes in, expect graceful failure
- `verifier caught a regression` — preset with a failing
  invariant, shows the red ✗ per case

**Export**: `main.py` + `verify.py` with the test report.

#### Tab 3 — "Durable Workflow"

**The T3.1 demo.** User sees a DAG execute, journal itself
to localStorage, then "crash" mid-step and resume from the
journal. Presets:

- `etl happy path` — 3-step DAG
- `step 2 fails` — Saga compensation in reverse
- `kill + resume` — mid-DAG crash, ResumeToken JSON, restart
- `7-day TestEnv` — virtual clock, 7-day sleep in <1s

**Export**: `dag.py` + `journal.json` for offline inspection.

#### Tab 4 — "A2A Federation"

**The T3.3 demo.** User starts a federated server (in a
worker thread inside the tab), opens a second tab to a
"peer" agent, and sees a task hand off between them.
Presets:

- `local two-agent` — both servers run in browser, peer
  discovery round-trips
- `remote discovery` — point at a public loopy-agent
  server (a tiny `playground.dream-pixels-forge.dev`
  deploy that we maintain for this purpose)
- `webhook verification` — receive a fake webhook, verify
  HMAC-SHA256, show what to do with the signature

**Export**: `agent.py` + `serve.py` for a deployable bundle.

#### Tab 5 — "Compliance + Cost Guard"

**The T2.2 + T2.3 demo.** User composes policies in a form,
watches them fire in real-time on a sample request, and
sees the cost-aware routing kick in. Presets:

- `PII block` — `pii_in_input` policy, PII is redacted,
  `block` decision halts the call
- `cost cap` — `max_cost_usd=0.01` against a 4-model
  gateway, fallback chain visible
- `audit log` — every policy decision appears in the
  panel, raw context (audit fidelity) + scrubbed (storage)

**Export**: `gateway.py` with policies + cost config.

## Part 2 — Roadmap: v1.1, v1.2, v1.3

### v1.1 — "The Adoptability Release" (4 weeks, target 2026-10-01)

> **Theme**: make loopy-agent effortless to discover, try, and
> adopt. Lower the activation energy from 3 hours to 3 minutes.

#### Theme 1 — Playground UI (the Part-1 deliverable above)

- **Why**: every great agent framework ships a playground.
  LangChain has LangSmith Playground, AutoGen has AG2 Studio,
  CrewAI has Crew Studio. loopy has nothing. This is the
  single biggest gap vs. user adoption.
- **Public API additions**: None (the Playground is JS/TS).
  Python-side: a `loopy playground --port N` subcommand
  (T3.3.2 follow-up) that boots a local server with the
  same code the wasm bundle runs.
- **Breaking changes**: None.
- **Dev plan milestones**:
  - PL.1 — Marketing site
  - PL.2 — Pyodide + first tab
  - PL.3 — All 5 tabs
  - PL.4 — Custom widgets
  - PL.5 — Export templates
  - PL.6 — SEO
  - PL.7 — Live deploy

#### Theme 2 — One-command project bootstrap

- **`loopy init <name>` CLI subcommand** that scaffolds a
  new project with:
  - `pyproject.toml` with `loopy-agent[all]` dependency
  - `agent.py` with a `TestModel`-backed `AgentLoop` that
    prints "hello world"
  - `loopy.yml` config file (new) with sane defaults
  - `.gitignore`, `README.md` with the 4 examples
  - One `pytest test_agent.py` that runs without any
    network or API key
- **Public API additions**: `loopy init`, `loopy.yml` schema
- **Why**: matches `npm init`, `cargo new`, `django-admin
  startproject`. First-time users should be one command
  away from a runnable example.

#### Theme 3 — Quickstart recipes (10)

A `examples/` directory with 10 hand-written, copy-pasteable
recipes covering the 80% use cases. Each recipe is a single
file < 100 lines. Examples:

1. `hello_world.py` — minimal AgentLoop
2. `streaming.py` — token-by-token output
3. `cost_capped.py` — gateway with max_cost_usd
4. `policies.py` — Compliance-as-Code example
5. `durable.py` — DAG + ResumeToken
6. `verified.py` — VerifiedAgent
7. `federation.py` — A2A handoff
8. `hitl.py` — interrupt + resume
9. `redaction.py` — PII scrubbing
10. `otel.py` — OpenTelemetry export

- **Why**: examples are the highest-ROI documentation
  investment for a developer framework. Every competitor
  has them; ours are weak.

#### Theme 4 — Improved error messages

Every `raise SomeError("...")` in the codebase gets
re-examined for:
- **What the user did wrong** (e.g. "you passed `max_steps=0`
  with `interrupt_after=['actor']`")
- **How to fix it** (e.g. "set `max_steps >= 1` or remove
  the interrupt config")
- **Link to docs** (e.g. "see
  https://loopy.dev/docs/agent-loop#interrupts")

- **Why**: error messages are the most under-rated
  developer-experience investment. We have ~200 raise sites;
  audit them all.

### v1.2 — "The Federation Release" (2–3 months, target 2026-12-01)

> **Theme**: turn loopy-agent from a single-process toolkit
> into a multi-tenant distributed runtime. Compete with
> AutoGen + LangGraph Cloud + CrewAI.

#### Theme 1 — Service-mode FederatedServer (T3.3 follow-up)

- `python -m loopy serve --workers N` with a real
  multiprocessing / asyncio task pool
- `POST /tasks/{id}/stream` upgrades SSE from
  single-shot to a long-lived stream
- `POST /tasks/{id}/cancel` becomes a soft-cancel that
  propagates to all peers in the cluster
- A2A handoff becomes async (the request doesn't block
  on the peer; the result is delivered via webhook or
  a follow-up poll)

#### Theme 2 — Multi-tenant gateway (T2.3 follow-up)

- `Gateway(tenant="acme")` partitions cost tracking, audit
  log, and rate limits by tenant
- `CostTracker.tenant_totals(tenant_id)` returns per-tenant
  breakdown
- `PolicyEngine(per_tenant=True)` so each tenant has its
  own policy set; policies are loaded from a per-tenant
  config dir

#### Theme 3 — Adaptive retry + backoff (T1.2 follow-up)

- `AgentLoop(retry_policy=Policy(...))` with exponential
  backoff, jitter, and circuit breaker
- Out of the box: `Policy.exponential(max_attempts=5,
  base=1.0, cap=30.0)` with full jitter
- Visible in the Playground's Retry tab

#### Theme 4 — Hot-reload + Dev server

- `python -m loopy dev` watches the project for changes
  and re-runs the affected loop on save
- Integrates with the Playground: changes in the editor
  show up live in the playground
- Includes a `loopy doctor` subcommand that diagnoses
  common misconfigurations (missing API key, mismatched
  Python version, broken virtualenv)

#### Theme 5 — Language server + editor integration

- `pip install loopy-agent[language-server]` installs
  a small LSP that provides:
  - Autocomplete for `PolicyEngine`, `Condition`, `Invariant`
  - Inline docs for every public symbol
  - `AgentLoop.run` step-by-step debugger
- **Why**: every modern agent framework ships an LSP.
  LangChain has `langchain-vscode`, AutoGen has
  `autogen-vscode`, CrewAI has nothing yet (we win
  this round).

### v1.3 — "The Federated Mesh Release" (6–9 months, target 2027-06-01)

> **Theme**: loopy-agent becomes the **kernel of a federated
> agent mesh** — agents discover each other, negotiate
> work, and learn from each other. This is where loopy
> stops being a toolkit and becomes a **platform**.

#### Theme 1 — Agent marketplace (T3.3 follow-up)

- `loopy registry publish` to push an agent to a public
  registry (think: PyPI for agents)
- `loopy registry install acme/web-search-agent` to
  consume a third-party agent
- Discovery via well-known DNS + Sigstore-verified agent
  cards
- Marketplace is the v1.0.0 FederatedServer scaled out;
  includes billing (with `Stripe` + L402 protocol) and
  per-call metering

#### Theme 2 — Cross-agent memory (T2.2 follow-up)

- `AgentMemory(tenant_id, scope="agent" | "cluster" | "global")`
  that lets agents share state without coupling
- Backed by Postgres + pgvector for semantic search
- Per-tenant encryption; row-level access control
- Visible in the Playground: "View agent memory" tab

#### Theme 3 — Agent learning (T3.2 follow-up)

- `LearnedAgent(agent, dataset)` where the dataset
  consists of `VerificationReport` failures
- Each failure generates a `CounterExample` and trains
  a small adapter on top of the base agent
- Evaluation: the same `VerificationSpec` must pass
  on the augmented agent within `k` epochs
- **Why**: this is the killer feature vs. AutoGen /
  LangGraph / CrewAI. None of them have a self-improving
  loop. With this, loopy becomes the only agent framework
  where shipping a verification spec is enough to make
  the agent reliable.

#### Theme 4 — Formal verification (T3.2 follow-up)

- `FormalVerifier(agent, spec, model_checker="z3" | "cvc5")`
- Compiles the agent's policy + verification spec into
  a model-checker query
- For deterministic policies, this gives sound
  verification (no false positives); for stochastic
  policies, it gives bounded-probability guarantees
- **Why**: this is the move from "we tested it on 50
  cases" to "we proved it works on all cases up to N
  steps". Wins a Tier-1 enterprise customer segment.

#### Theme 5 — `loopy serve` (the long-promised TL6 deliverable)

- Production-grade multi-tenant agent hosting
- Per-tenant rate limits, cost caps, audit logs
- Horizontal scaling (Kubernetes-native)
- RBAC + SCIM provisioning
- SOC2 controls already met (from the v1.0.0 work)
- Status page, SLO monitoring
- **Why**: this is the move from "library" to "service".
  Competes with LangGraph Cloud + OpenAI Assistants +
  Vertex AI Agent Engine.

## Risks and open questions

1. **Pyodide size** — a 25 MB bundle is borderline for first
   load on slow networks. Mitigation: pre-load in a service
   worker, cache aggressively.

2. **Browser sandboxing** — the user's agent code runs in
   Pyodide, not Node. This means no native file I/O, no
   network beyond Pyodide's own socket layer. Documented as
   a constraint: "the playground is for trying features,
   not for production runs."

3. **Maintained forever?** — A Playground is a maintenance
   burden. Every time a public API changes, every preset
   needs updating. We need a CI job that runs the playground
   smoke tests on every PR.

4. **Pyodide + our dependencies** — `httpx`, `pydantic`,
   `tenacity`, etc. all need to work in Pyodide. Pyodide
   ships a minimal `pydantic` and `httpx`; we need to
   verify the full dep tree compiles to WASM.

5. **LSP scope creep** — a real LSP is a 6-12 month
   investment. v1.2's LSP is intentionally minimal
   (autocomplete + inline docs); advanced features
   (debugger, refactor) are v1.3+.
