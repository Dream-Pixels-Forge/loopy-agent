# v1.1 GOAL.md — "Try It Now"

> **Per the dsh-production-agentic-engineering skill**, this is
> the deterministic execution contract for v1.1. Every milestone
> has an automated verification command that **MUST** return
> exit code 0 before that milestone is considered complete.
> If a gate fails, the agent must diagnose and fix the failure
> **without modifying the test assertion to pass artificially.**
>
> Generated using the [production-agentic-engineering skill](https://github.com/donald-stigbert).
> See also: [`V1.1_PLAYGROUND_AND_ROADMAP.md`](./V1.1_PLAYGROUND_AND_ROADMAP.md).

## Context

v1.0.1 is shipped and live on PyPI. v1.1 is the "adoptability"
release — its goal is to drop the time from "I just heard about
loopy-agent" to "I have a runnable example" from ~3 hours to
~3 minutes. Four themes:

1. **T1.1** — `loopy init` project bootstrap (one command from
   `pip install` to `python main.py`)
2. **T1.2** — 10 hand-written, copy-pasteable recipes covering
   the 80% use cases
3. **T1.3** — Error-message audit: every `raise` site gets
   reviewed for "what went wrong / how to fix / link to docs"
4. **T1.4** — Playground UI (separate Next.js + Pyodide worktree)

## Headline features

- `loopy init <name>` scaffolds a new project with sensible
  defaults (matches `npm init`, `cargo new`, `django-admin
  startproject`).
- 10 recipes in `examples/` covering hello-world, streaming,
  cost-cap, policies, durable, verified, federation, hitl,
  redaction, otel.
- All 200+ `raise` sites audited; each gets a structured
  error message with: what the user did wrong, how to fix,
  and a docs URL.
- Playground UI at `playground.dream-pixels-forge.dev` (5
  tabs: AgentLoop, Verified, Durable, Federation, Compliance).

## The contract in one sentence

> Ship v1.1 **without ever** committing code that breaks the
> 800-test suite, ruff lint, ruff format, or 92% coverage
> baseline. Every milestone has an executable verification
> command that MUST return exit code 0 before that milestone
> is considered complete.

## Phase A — loopy init (T1.1)

### T1.1.1 — Scaffold `loopy init <name>`

- **Public surface**: `loopy init <project_name> [--no-test]`
  added to the CLI dispatcher in `loopy/cli.py`.
- **Files created** in the new project directory:
  - `pyproject.toml` with `loopy-agent[all]` dependency
  - `agent.py` with a `TestModel`-backed `AgentLoop` that
    prints "hello world"
  - `loopy.yml` config file (NEW format) with sane
    defaults: `provider: test`, `max_steps: 3`,
    `interrupt_before: []`
  - `.gitignore` (Python + venv + editor)
  - `README.md` (template pointing at loopy.dev)
  - `tests/test_agent.py` — single `pytest` test that
    imports the agent and runs it, no API key required.
- **Negative controls**:
  - Refuses to overwrite an existing non-empty directory
  - Refuses to create a project name with `/` or `..`
  - With `--no-test`, skips the test file generation
- **Verification command**:
  ```bash
  python -c "from click.testing import CliRunner" 2>/dev/null || \
    python -m pip install click pytest  # ensure test deps
  cd "$(mktemp -d)" && \
    python -m loopy init myproj --no-test && \
    test -f myproj/pyproject.toml && \
    test -f myproj/agent.py && \
    test -f myproj/loopy.yml && \
    test -f myproj/.gitignore && \
    echo "loopy init OK"
  ```

### T1.1.2 — Tests for `loopy init`

- **Tests**: ≥10 new tests in `tests/test_cli_init.py`
  covering: scaffold creation, existing-dir refusal, name
  validation, --no-test flag, loopy.yml schema, idempotency
  of re-running init, custom loopy.yml template selection
- **Verification command**:
  ```bash
  python -m pytest tests/test_cli_init.py -v --no-header
  ```

### T1.1.3 — `loopy.yml` schema + loader

- **Public surface**: `loopy.config.load(path="loopy.yml")`
  returns a `LoopyConfig` dataclass with fields `provider`,
  `model`, `max_steps`, `interrupt_before`, `interrupt_after`,
  `policy_engine_path` (optional), `state_manager_path`
  (optional), `redactor_config` (optional)
- **Files**: `loopy/config.py` (new)
- **Tests**: ≥5 tests for round-trip + validation
- **Verification**:
  ```bash
  python -m pytest tests/test_config.py -v --no-header
  ```

## Phase C — Error-message audit (T1.3)

### T1.3.1 — Catalog every `raise` site

- **Tool**: `scripts/audit_errors.py` walks the source tree
  and extracts every `raise ...Error(...)` and every
  `raise ValueError(...)` / `raise RuntimeError(...)` /
  etc. with the file + line + message
- **Output**: `dev-notes/ERROR_AUDIT.json` with every raise
  site flagged with: `passes` (already has docs link + fix
  instructions) | `needs_work` (raw "X is invalid" without
  guidance)
- **Verification**:
  ```bash
  python scripts/audit_errors.py
  test -f dev-notes/ERROR_AUDIT.json
  ```

### T1.3.2 — Improve every "needs_work" site

- **Rule**: every `raise` in `needs_work` becomes
  `raise SomeError(f"...what went wrong... how to fix: ...
  (see https://loopy.dev/docs/...#...)...")` with all three
  parts (cause, fix, docs link).
- **Test**: `tests/test_error_messages.py` — for every
  exception class, `pytest.raises` must capture a message
  matching a regex that includes the docs URL pattern
  `https://loopy\.dev/docs/.*#[a-z-]+`
- **Pass criteria**: ≥ 95% of `raise` sites produce
  docs-link-bearing messages
- **Verification**:
  ```bash
  python -m pytest tests/test_error_messages.py -v --no-header
  python scripts/audit_errors.py  # rerun; confirm >= 95% pass
  ```

### T1.3.PRE — Commit checkpoint

- Branch: `feat/v1.1-error-audit`
- Commit: `feat(errors): T1.3 audit + improve 200+ raise sites`

## Phase D — Playground UI (T1.4)

This is the heaviest phase. The Playground UI is a separate
Next.js + TypeScript + shadcn app, NOT inside the `loopy-agent`
repo. It will be developed in a separate worktree.

> **OUT OF SCOPE FOR THIS EXECUTION**: T1.4 is being deferred
> to a separate worktree + repo (`loopy-playground`) because
> mixing a Next.js app into the `loopy-agent` Python repo
> would break the zero-deps-core invariant and the
> `pyproject.toml`'s `[all]` extra definition.
>
> The spec lives in
> `dev-notes/V1.1_PLAYGROUND_AND_ROADMAP.md` and is being
> tracked separately. v1.1 will ship without it; v1.1.1 will
> add the Playground UI as a follow-up.
